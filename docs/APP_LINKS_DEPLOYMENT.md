# Android App Links — how the file is served and verified

> **Status 2026-11-17:** `https://lovemcq.com` is live (web + `/api/v1` 200).
> The identity files are generated by the **Laravel server**, not copied into
> `public/`. Package identity is `com.beardbishwo.lovemcq`.

Android verifies `https://lovemcq.com` links against a file published by the
**server**:

```
https://lovemcq.com/.well-known/assetlinks.json
Content-Type: application/json
```

## Where the values live

`PwaIdentityController` (web repo, `app/Http/Controllers/PwaIdentityController.php`)
serves both `.well-known/assetlinks.json` and
`.well-known/apple-app-site-association` from `config('mobile.identity.*')`.
Those values are overlaid at runtime from the `settings` table, so the
authoritative editor is:

**`/admin` → Settings → Mobile App Settings → “Store identity & app links”**

| Field | Current value |
|---|---|
| Android application ID | `com.beardbishwo.lovemcq` |
| iOS app ID | `TEAM_ID.com.beardbishwo.lovemcq` (Apple Team ID still pending) |
| Android SHA-256 fingerprints | upload key below (+ Play App Signing key when enrolled) |

The same Android package name is used by Play Integrity
(`mobile.integrity.play.package_name`).

### Never restore a static file

An earlier release copied `assetlinks.json` into `public/.well-known/`.
Apache serves a real file before the Laravel front controller, so that copy
shadows the config-driven route forever — SCP deploys never delete it. The
server deploy workflow now removes both legacy files on every deploy. Do not
add them back.

| Field | Value |
|---|---|
| package | `com.beardbishwo.lovemcq` |
| SHA-256 (colon hex) | `21:D8:6E:E5:00:01:3B:5E:BE:13:E2:13:C9:6F:C2:DB:74:1F:AA:B8:EB:7D:95:8C:B7:19:B4:58:21:8A:D4:1E` |
| SHA-256 (base64, freeRASP) | `sha256/Idhu5QABO16+E+ITyW/C23QfqrjrfZWMtxm0WCGK1B4=` |
| source of truth | `android/app/upload-keystore.jks`, alias `upload` (verified 2026-11-17) |

Both encodings are the same certificate. The admin panel accepts colon hex,
bare hex or base64 and normalises to colon hex on output.

## Debug vs release builds

A `flutter build apk --debug` is signed with the machine's **debug** key, which
is not the upload key — App Links will not verify for a debug install even
though the app handles the same paths. Use a release/sideload build signed with
`android/app/upload-keystore.jks` when testing `https://lovemcq.com` links.

## Play App Signing — the trap

If the app is enrolled in Google Play App Signing (the default for new apps),
Google re-signs the AAB with an **app-signing key** that is not this upload
key. `assetlinks.json` must then contain **both** fingerprints:

* the upload key above (used by local/release builds you install yourself),
* the **app signing key SHA-256 from Play Console → Release → Setup → App
  signing** (used by installs from the Play Store).

With only the upload key, links verify on a sideloaded build and fail on every
Play-installed build. Paste the second value into the admin field as an
additional entry.

## Verify

```bash
curl -s https://lovemcq.com/.well-known/assetlinks.json
adb shell pm get-app-links com.beardbishwo.lovemcq
adb shell pm verify-app-links --re-verify com.beardbishwo.lovemcq
```

`get-app-links` must report `verified` for `lovemcq.com`. Until then, an
`https://lovemcq.com/...` link opens a browser; the `civilcal://` scheme is
unaffected and always works.
